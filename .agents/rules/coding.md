# Правила разработки

## Нормативные слова и приоритет

- **ОБЯЗАН** — требование без исключений в пределах задачи.
- **ЗАПРЕЩЕНО** — действие не выполняется без нового явного согласования пользователя.
- **Нетривиальная логика** — код с ветвлением, циклом, парсингом, преобразованием данных, доступом к внешней системе, операциями с деньгами или безопасностью.
- При конфликте соблюдайте явный согласованный план пользователя и более строгое требование. Если конфликт не разрешён, остановитесь и запросите уточнение.

## До изменения кода

1. Прочитайте задачу, затрагиваемый код, вызывающие места, тесты, фикстуры, конфигурацию и экспорты.
2. Определите конечное поведение, затронутые контракты, риск потери или раскрытия данных и проверяемые критерии успеха.
3. Явно перечислите существенные предположения. Если возможны разные результаты, область, риск или контракт, остановитесь и запросите уточнение; не выбирайте вариант самостоятельно.
4. Для многошаговой задачи составьте план с файлами, поведением, тестами и проверками. Не изменяйте файлы до согласования плана.

## Выбор решения

Выбирайте первое решение из списка, которое полностью выполняет согласованный контракт:

1. Не добавлять возможность, если она не нужна для цели задачи.
2. Переиспользовать существующий код и принятый в проекте паттерн.
3. Использовать стандартную библиотеку или встроенную возможность платформы.
4. Использовать уже установленную зависимость.
5. Добавить минимальный понятный код.
6. Добавить новую зависимость только при отсутствии равноценного решения выше и после согласования.

ЗАПРЕЩЕНО добавлять не запрошенные возможности, параметры, конфигурацию, обёртки, преобразования типов, абстракции и код «на будущее». Короткий код допустим только если он не ухудшает читаемость, корректность и обработку граничных случаев.

## Изменение кода

- Изменяйте только строки и файлы, необходимые для согласованного поведения. Каждая изменённая строка должна быть связана с задачей.
- Следуйте существующим структуре, именованию, слоям и обработке ошибок. Не изменяйте несвязанные комментарии, форматирование и код.
- Удаляйте только неиспользуемый код, который появился из-за текущего изменения. О найденных ранее проблемах сообщайте отдельно.
- Перед исправлением дефекта найдите все вызывающие места изменяемой функции и исправляйте общую первопричину, а не отдельный симптом.
- При переносе или объединении кода сохраняйте его валидацию и обработку ошибок.
- Не добавляйте обработку сценария без реалистичного источника, но ОБЯЗАНЫ сохранять и добавлять проверки на границах доверия, защиту от потери данных, безопасность и требуемую обработку ошибок.
- Комментарий допустим только для причины, которую нельзя понять из кода. Известное временное ограничение оформляйте так: `shortcut: <ограничение>, <условие пересмотра>`.

## Тестирование и проверка

- Для нетривиальной логики ОБЯЗАН быть хотя бы один тест или assert-проверка, подтверждающая новое поведение.
- Для внешнего ввода ОБЯЗАНЫ быть проверки валидного, невалидного и граничного ввода. Для безопасности — проверки отказа в доступе и отсутствия раскрытия чувствительных данных, когда такие данные или доступ существуют в контракте.
- Исправление дефекта ОБЯЗАНО иметь тест, воспроизводящий дефект, если его возможно стабильно воспроизвести.
- Выполняйте релевантные проверки из согласованного плана и фиксируйте их фактический результат. Успешный запуск команды не заменяет проверку затронутого контракта.
- При падении теста установите и зафиксируйте причину. Не изменяйте продуктовое поведение только ради прохождения теста; если нужно изменить поведение, остановитесь и получите отдельное согласование.

## Завершение работы

Сообщите выполненные изменения, фактически выполненные проверки, непроверенные области и остаточные риски. Не заявляйте о завершении или прохождении проверки без подтверждающего результата.
